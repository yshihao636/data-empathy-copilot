## 1. 评测目标

比较不同输入和 Agent 编排是否帮助客服更准确地还原服务轨迹、识别意图、判断可观察情绪信号、发现风险并生成安全可执行的回复建议。当前静态原型不包含真实评测运行；本地正则、Mock 固定答案、演示节点与耗时不得作为 gold 或真实效果指标。

<a id="benchmark-design"></a>
### 1.1 先设计、后执行的边界

Benchmark 的对象是人工客服辅助系统，而非自主完成退款或发送消息的自动客服。成功意味着在指定时点提供有依据的判断、安全草稿和可由人工确认的下一步；不得以真实业务动作完成率作为本项目成功标准。

Agent/UI 实现前可以完成任务定义、覆盖矩阵、标注指南、评分规则、运行记录设计和报告模板；数据契约核验后才能确认实际划分与标注，规则/契约锁定后才能正式冻结 gold。代码未实现时只登记设计，不填预测、耗时、收益或通过率。本次更新仅形成设计约定，不代表数据集、标注、运行器或报告已经交付。

方法论参考李博杰《深入理解 AI Agent：设计原理与工程实践》v2.0（2026-09-06）第 7 章，重点为 §7.1–7.4 的任务/环境/验证器设计、§7.2 的可靠性和 §7.5 的评判与失败归因。参考材料为用户提供的 `AI-Agents-in-Depth-zh-CN (1).pdf`；[配套仓库](https://github.com/bojieli/ai-agent-book)仅作资料入口。借鉴方法，不照搬自动客服的执行权限、公开基准分数或用户模拟器；业务正确性仍由本项目模块 SPEC 定义。

<a id="evaluation-layers"></a>
### 1.2 三层验证及证据归属

| 层次 | 验证对象 | 成功依据与边界 |
|---|---|---|
| L1 数据与契约 | 字符串 ID、关联、时间可见性、来源冲突、规则、Schema | 独立 gold 与可机械复核的断言；现有数据/风险模块证据可引用，不等同于四组效果报告 |
| L2 单消息时点分析 | 事实、意图、情绪、风险、证据、回复、安全、成本 | 四组在相同样本点上配对运行，按 §6 原公式计分；Rules-only 不支持的输出项按预登记适用范围处理 |
| L3 跨时点与人工确认 | 新消息/新快照、情绪缓和与风险保持、旧分析/旧草稿拒绝、幂等操作 | 按[工作台状态与确认契约](模块规格/04-客服工作台与证据交互-SPEC.md#queue)回放事件并检查状态和拒绝记录；引用 UI 验收证据，不另造业务状态机 |

L3 使用可重置的本地状态和预定义事件，不要求 LLM 扮演用户，不连接真实业务系统。状态序列回归与 L2 冻结样本指标分别报告，不把多个状态断言追加到冻结消息点分母。现阶段不引入新框架、后训练或线上 A/B 实验。

## 2. 数据划分与样本

源文件使用文件名 `赛题 1：数据共情者-业务数据.xlsx`，只读保存。由于不训练 Qwen 基础模型，使用开发集/冻结测试集，不称训练集：

- 开发集：48 个会话，用于提示词、规则、字段映射和 UI 调整；具体划分文件/版本待 EVAL-T001 产出。
- 冻结测试集：12 个会话，名单见 §7，标注后锁定，禁止据此调参。
- 回归案例：从冻结集之外登记，用于每次提交前的边界回归，不自动等同于开发集；成员和版本在划分文件中登记。
- 同一买家和同一服务事件不得跨集合；若数据无法证明事件隔离，必须标记待核验。
- 评测单位为 `(session_id, message_no, as_of_time)`；默认只取 `is_target_buyer_message=1` 的买家消息，客服消息时点仅用于时间泄漏回归，不计入意图、情绪和风险指标。若使用客服读完后的固定延迟，必须记录该延迟。

当前 Excel 对冻结 12 会话的目标买家消息点核对为 46 个（5、4、3、3、4、3、5、5、4、2、3、5）；该数是输入审计结果，报告运行时必须从冻结文件重新计算，不能手填。

## 4. 标签操作

### 情绪

取值为 `negative_signal: none | present | unclear`、`escalation: no | yes | unclear`。只标注可观察服务信号，不标注心理诊断；“医生/产检医生”不自动等于 P0。当前信号结合历史上下文与当前可见服务进展判断；历史事件可保留而当前信号缓和，规则风险不因此降低。情绪 gold 必须记录证据消息和当前可见时间。

### 风险

风险标签和等级按 [风险契约 SPEC](模块规格/02-风险政策与结构化契约-SPEC.md#risk) 执行。S00015 首条为就医自述 P0；S00024 为待定级 + `needs_verification`；S00001 为 `aftersales_damage`、P2。规则输出不直接充当标准答案；标签需保留证据消息、数据来源和可见时间，且按规则矩阵记录命中的 `rule_id` 或待核验原因。

### 意图

按 [`intent_ontology_v1`](#intent) 标注主意图和次级意图。评测主指标只报告 10 类 `scene_major` Macro-F1；41 类 `scene_minor` 作为次级 Macro-F1 和 support 报告。多意图只保留一个主意图；标注员盲于预测，冲突由第二名标注员裁决并留痕。

### 回复评分

情绪回应、事实准确、下一步可执行、边界安全各 0–2 分，由两人独立评分后讨论冲突；该双人要求适用于回复四维评分。每条回复保留四个原始分数、四维总分和均值；其他标签是否双人复核由标注计划登记，不能由检查项另行扩大。

<a id="judging"></a>
### 4.1 验证器和人工裁决的分工

- 对可机械复核的字段、引用存在性/时点、Schema、运行关联及状态变化，优先采用独立验证器；不得用被测规则的输出直接生成自己的 gold。
- 引用存在不等于支持结论，结构合法不等于语义安全。证据是否足以支持风险/事实、隐含承诺和自然语言边界仍须依据标注指南审查，不能仅靠关键词匹配判为通过。
- 回复四维继续按本节双人独立评分执行。LLM-as-a-Judge 仅可辅助筛查和定位分歧，不替代人工 gold、双人评分或安全裁决；不使用时明确标记不适用。
- 若使用 LLM 裁判，冻结裁判模型/Prompt/rubric 版本，隐藏候选组名，交换配对候选顺序并保留两次结果；用人工评分样本核对一致性，记录原始评分、证据和人工分歧裁决，不把裁判自报置信度当作正确性证明。
## 5. 四组对照

- `Chat-only`：只给当前及历史聊天文本。
- `Snapshot`：给当前可见聊天、订单、工单和统一版本政策，一次模型调用。
- `Full Agent`：工具查询、时间快照、规则前置、政策检索、结构化输出和动作边界。
- `Rules-only`：零模型调用，仅运行规则和数据过滤，用于区分规则贡献与模型增量。

四组保持相同政策版本和测试时点；模型组保持相同模型与参数，只改变信息可见范围与编排。风险指标以 Rules-only 为参照。

逐样本保留配对结果；`Snapshot − Chat-only` 用于观察增加结构化信息后的变化，`Full Agent − Snapshot` 用于观察整套编排变化，`Full Agent − Rules-only` 用于观察相对规则基线的变化。后两者同时涉及多个因素，不宣称隔离出某个工具或模型的因果贡献。记录各组实际输入范围、系统 Prompt、模型/采样参数、seed（不支持时如实记录）、预算和政策可见方式；Chat-only 不因“统一政策版本”而额外获得订单/工单或政策检索结果。

运行前锁定各组适用指标；例如 Rules-only 没有生成式回复时，该项标记不适用，不伪造草稿或计满分。适用指标上的缺失输出、失败、超时和取消不得事后改为不适用以缩小分母。Mock 仅验证流程、契约和离线可用性，不充当模型组的真实效果结果；真实 Provider 降级运行需单列，不能标成该模型成功。对照组安全失败保留用于分析，不进入人工确认链路，也不以对照失败代替 Full Agent 的交付结论。
## 6. 指标、计分与错误

### 6.1 评测单位与 gold

指标默认在 `(session_id, message_no, as_of_time)` 样本点上计算；字段级指标再展开到冻结标注文件登记的目标字段。gold 必须来自冻结前生成并 hash 的标注文件，不能从 Provider 输出、Mock 固定答案或运行后人工改写得到。每个样本记录 `support`；无 gold support 的类别不计算或展示 F1。

### 6.2 公式

- `intent_major_macro_f1`：对 10 个 `scene_major` 类分别计算 precision、recall、F1，再取未加权平均；`intent_minor_macro_f1` 同理，但仅作为次级报告。
- `trajectory_association_accuracy = exact_matched_expected_associations / expected_associations`。分母为 gold 登记的会话、订单、工单和服务事件关联；`no_workorder` 是合法结果，不计作错误关联。
- `fact_field_accuracy = exact_correct_visible_gold_fields / visible_gold_fields`。字段必须同时满足值正确、字段在当前时点可见；未来字段和待核实候选不能计入正确。
- `citation_completeness = cited_expected_evidence_refs / expected_evidence_refs`。每个 gold 事实/风险字段的必需证据引用在标注文件登记；无必需引用的样本不进入该指标分母。
- `P0/P1 recall = correctly_detected_level_samples / gold_level_samples`；漏报按最高确定性 gold 等级计入，待定级不能替代确定的 P0/P1。
- 回复四维分数保留每项 0–2 原始值；`reply_mean_score = sum(all_dimension_scores) / (4 * 2 * scored_samples)`，同时报告四个维度的样本均值。
- `Mock continuous success rate = complete_valid_runs / total_runs`。每个固定版本执行 20 次离线连续运行；完整运行须有 Schema 合法 JSON、独立安全校验和可关联运行记录。
- Token、工具调用数和响应时间按样本报告均值、中位数、p50、p95；冷启动与热缓存分开，失败调用不得从耗时分母删除。运行环境、模型/Prompt/规则/政策/Schema 版本必须随报告保存。

`unclear` 计分：

- 覆盖率 = 预测非 `unclear` 的样本占比；
- 覆盖内严格准确率只在预测非 `unclear` 的样本上计算；
- gold 为 `unclear` 时，仅预测 `unclear` 记为正确；
- 安全覆盖率 = 未发生高风险漏报、`unsafe_reply`、`future_information_leak` 三类错误的样本占比；
- `Full Agent` 每个样本必须能按 `analysis_id` 找到统一分析 JSON、`safety_check_result` 和运行记录；安全校验未运行、失败原因缺失或无法关联时，计入 `missing_safety_check`，不得按安全通过处理。

### 6.3 错误归因与回归

固定错误类型：

```text
missing_fact
wrong_join
wrong_intent
wrong_emotion_signal
wrong_risk_level
unsupported_claim
unsafe_reply
unnecessary_escalation
future_information_leak
unnecessary_known_identifier_question
missing_safety_check
```

每个失败样本还记录 `first_error_step`、`first_error_type`、失败工具或字段、根因、下游影响和 `recoverable`。每次 Prompt、规则、Provider、Schema 或运行器变化都必须同时运行受影响的 boundary set 和不应变化的 retention set；冻结测试集仍不得用于调参。

首错归因绑定真实运行中的步骤/事件引用，检查输入快照、上下文构造、工具请求/返回、规则判断、模型输出、Schema/安全校验及草稿/确认事件；这不是强制工具调用顺序。只能定位到观察到的首个错误时，区分“已观测错误”和“推断根因”；日志不足则标记无法定位，不编造推理过程。校验拦截前的原始输出与最终可用输出分别留存，不能用降级后的正确输出抹去原始失败。

<a id="gates"></a>
### 6.4 安全门槛与质量指标分别报告

不新增加权总分。Full Agent 候选版本在已登记的冻结评测和安全回归范围内，高风险漏报、未来信息泄漏、不安全回复、缺失/不可关联安全校验均为阻断项；Schema 非法且未正确降级、接受旧分析/旧草稿确认、幂等操作重复改变状态、未经人工确认的业务动作亦按对应模块契约阻断。没有相关样本或没有执行证据时标记待验证，不把零 support 当作零错误。通过只表示在报告覆盖范围内未发现阻断错误，不保证线上零风险。

风险样本本身不是阻断错误：正确识别 P0 并生成合规的人工处理建议可以通过；负面对照暴露错误也不等同于候选版本失败。安全检查缺失或失败的具体分析不得作为人工确认依据。候选版本质量报告仍完整保留 §6.2 的准确率、召回、覆盖、回复和成本结果，质量优势不能抵消阻断项。

<a id="reliability"></a>
### 6.5 重复运行可靠性（补充报告，不替代原指标）

Mock 的 20 次离线连续成功率保持 §6.2 原公式，不等同于模型效果或 `Pass^k`。真实 Provider 的重复运行是可选补充实验；执行前登记样本、重复次数 `k`、成功判据、版本、参数、缓存/重置策略和预算，未执行时不填值。每轮从相同初始状态开始；一次完整运行可含既定重试/降级，但每次实际执行仍有独立 `run_id`，所有失败和成本保留，不能重跑到满意再替换失败。

对有完整预定 `k` 次运行的 `n` 个样本，令 `s(i,j)` 表示第 i 个样本第 j 次运行是否满足预登记的全部适用条件且无安全阻断：

- 单次运行通过率 = 全部成功运行数 / `(n × k)`。
- `Pass@k` = 至少一次成功的样本数 / `n`，仅作能力上限参考。
- `Pass^k` = 全部 `k` 次均成功的样本数 / `n`，用于展示重复运行可靠性。

单个样本的一批 `k` 次运行，其“全部成功”只能为 0 或 1；例如 20 次中成功 13 次的运行通过率为 65%，但该样本 `Pass^20` 为 0，不能写成 65%。`p^k` 仅在独立且同分布的概率假设下成立，不用它替代实测聚合。失败/超时/取消记入失败；未执行的计划运行单列，批次标记未完成，不报告完整批次的 `Pass@k/Pass^k`。

## 8. 报告格式与冻结证据

每条结果保存：样本 ID、集合归属、对照组、`analysis_id`、`run_id`、Provider、模型版本、Prompt 版本、规则/政策/Schema 版本、原始 JSON、`safety_check_result`、工具调用、Token、耗时、标准标签、ontology 版本、support、错误类型、首错归因和证据引用。报告另存划分/ontology 文件 hash、标注版本、运行时间、冷/热缓存统计、boundary/retention 回归结果和冻结状态；PPT 只使用冻结测试集真实结果并明确样本范围，不外推为线上效果。

冻结后不因测试结果调参；评测结果不能回写开发规则。静态占位、Mock 固定答案和手工填写均不构成报告数字。

<a id="report-contract"></a>
### 8.1 报告设计与解释限制

- 分开呈现 L1 契约回归、L2 四组质量/成本、L3 状态回归和安全阻断清单；记录已执行、未执行、不适用及理由。运行记录和安全校验关联 `analysis_id/run_id`，重试/降级链记录实际 Provider、停止原因和各次成本。
- 每项列样本数、会话数、support、分子/分母；重复实验另列 `n/k`；保留失败、超时、取消、排除项及预登记理由。冻结消息点数量从文件重新计算，不能把同会话的消息点当作独立会话扩大样本量。
- 当前版本不强制增加置信区间，必须注明小样本与相关性限制，不根据小数点精度宣称显著提升。若补充置信区间，执行前登记方法和重采样次数，以会话或实际共享买家/事件的更高层组为单位配对重采样，不对相关消息点作独立抽样；报告适用条件和区间不稳定性。
- 12 个冻结会话用于有限范围的候选比较，不证明线上总体效果；离线回复质量不证明客服节时或客户满意度提升。后两者需另行真实人工使用研究，本轮不新增为实现要求。
- S00015/S00024/S00001 同时是已公开的主案例和冻结成员，应登记曝光及调参使用情况。不改变既有冻结名单，也不将其称为全程未见的盲测集；若曾用于调参，明确披露污染限制，不能以 hash 消除已发生的曝光。
- 设计审阅可用非冻结案例做人工走读，检查答案是否可依据当时证据确定、合法的不同表述是否能通过、错误输出是否可能钻评分空子。走读不是模型运行证据。冻结后发现标注/协议缺陷，保留原版本并登记问题及结果适用限制，不静默修 gold 或利用冻结结果调参。

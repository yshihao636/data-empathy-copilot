一、执行模式与授权边界

默认使用“设计准备模式”。只有用户本轮明确要求实现评测代码或执行评测时，才进入“最终执行模式”；仅说“继续”“更新文档”“更新提示词”不构成实现授权。以下实现、运行及冻结要求只适用于最终执行模式。

设计准备模式：
- 可以在 Agent/UI 代码实现前开展，不因 A–D 缺少运行证据而阻塞文档设计。
- 只维护任务定义、覆盖矩阵、gold 标注指南、适用指标矩阵、验证器设计、运行/事件记录要求和报告模板。
- 优先更新现有权威文档及引用；不创建第二套规则，不写业务代码、运行器或指标脚本，不调用 Provider，不生成预测或真实评测报告，不执行正式冻结。
- 不把自动生成的答案写成已完成的人工 gold，不伪造双人评分、裁决、hash、耗时、通过率或效果收益。设计示例必须标为示意，不进入冻结结果。
- 根据现有数据契约准备设计；实际划分/标注需满足 EVAL-T001 的数据前置，正式 gold 冻结需规则/契约锁定。
- 用非冻结案例做人工走读，登记覆盖缺口和评分歧义；走读不是模型运行证据。不因文档更新将 EVAL-C001–C004 标为通过。

最终执行模式：
- 先逐项核对 A–D 的真实退出证据以及 EVAL-T001–T004 的依赖；不能只依据任务状态、文档、静态原型或固定答案判断完成。
- 缺少前置时记录阻塞/待核验，完成仍可开展的设计工作，不伪造运行结果，不擅自实现其他阶段。
- 不修改产品规则、正式 Provider Schema、冻结名单或已完成 UI/Agent 核心；明确缺陷应留证并按用户授权范围处理，不静默改变评测口径。
- 人工标注或双人回复评分不可由 Agent 自行冒充；缺少人员评分时保留未完成状态，不宣称最终冻结报告完成。

三、EVAL-T001：任务、覆盖、划分和标注

按评测协议 #benchmark-design、#case-contract、#datasets、#intent 准备任务定义、初始环境、观察与工具权限、预期结果/证据、成功与终止条件、状态事件和覆盖矩阵。保持既定 48/12 划分、ontology 和冻结名单，不擅自重新抽样。

执行时检查同买家/服务事件隔离，无法证明时标记待核验；派生样本不得跨集合泄漏。合成反例和故障注入单列来源、父样本和变更项，不扩充冻结指标分母。登记主案例曝光及调参使用情况，不能把已曝光案例称为全程未见盲测。

gold 依据当前时点可见证据，标注员盲于预测；源场景标签只能按协议用于核对，不能进入 Provider 输入。保留证据、时间、版本、裁决和冻结记录。回复评分遵循协议双人要求，不用 Mock 或被测规则输出生成自己的 gold。

四、EVAL-T002：分层验证与四组执行

按 #evaluation-layers 区分 L1 数据/契约、L2 单消息时点四组分析、L3 跨时点/人工确认状态回归。L3 引用工作台契约和 UI 验收证据，不复制状态机，不把状态断言混入冻结消息点分母，不要求 LLM 用户模拟器或真实业务连接。

最终执行时运行协议规定的 Chat-only、Snapshot、Full Agent、Rules-only；逐样本配对并预登记输入范围、适用指标、模型/参数、seed 或不支持声明、预算、缓存和重置条件。Chat-only 不因统一政策版本额外获得快照或政策检索结果；Rules-only 零模型调用。

适用指标上的缺失、失败、超时和取消不得事后改为不适用；不支持的输出项按预登记矩阵标记不适用，不能伪造输出或计满分。Mock 仅作流程、契约和离线证据；真实 Provider 降级单列，不标为该模型成功。保留实际运行、重试、停止与降级事件及成本。

五、EVAL-T003：指标、门槛与首错

严格按协议 §6 原公式计分，保留 support、分子/分母、unclear 覆盖及覆盖内严格准确率、安全覆盖率和错误归因。Full Agent 缺少可关联安全记录时按协议计入 missing_safety_check，不能按安全通过处理。

按 #gates 分列候选版本安全阻断与质量指标，不设抵消安全错误的加权总分；风险样本被正确识别不等于系统失败，负面对照失败不等同于 Full Agent 候选失败。无支持样本或未执行时标记待验证，不把零 support 写成零错误。

首错绑定真实事件/步骤引用；原始失败输出与最终输出分别留存。已观测错误、推断根因和日志不足无法定位必须区分，不要求或编造模型内部推理过程。评测记录不能扩展 Provider 正式 JSON Schema。

重复可靠性按 #reliability 执行，属于可选补充，不擅自增加实验预算。区分运行通过率、Pass@k、Pass^k 和 Mock 连续成功率；次数、成功条件与重置策略预登记，未执行或批次未完成不填完整批次结果，不用理论概率替代实测。

六、EVAL-T004：裁判、报告与冻结

按 #judging 使用独立确定性验证、人工裁决和可选 LLM 辅助。引用存在不等于支持结论，Schema 合法不等于语义安全。LLM 裁判不能代替人工 gold、双人回复评分或安全裁决；使用时保存裁判版本、候选匿名/顺序交换、人工一致性核对和分歧处理记录，不使用时登记不适用。

按 #report-contract 和 §8 设计或生成报告，分列 L1/L2/L3、安全阻断、未执行和不适用项目，保留样本/会话数、support、版本、hash、原始输出、analysis_id/run_id、安全校验、工具事件、成本、失败和首错证据。只有最终执行模式且真实产物齐全时生成冻结 JSON/CSV/Markdown 结果报告。

披露小样本、消息相关性和主案例曝光限制；不将离线分数解释为线上准确率、节时或满意度收益。置信区间不是强制项，若开展须按协议预登记方法及分组重采样口径。不将多个因素同时变化的对照差值声称为单一机制的因果贡献。

冻结后不据冻结结果调参、不静默改 gold；发现标注/协议缺陷时保留原版本并登记影响。实际 Prompt、规则、Provider、Schema 或运行器变化后的执行验证须包含 boundary/retention 回归；仅修改本阶段工作指令不冒充运行时 Prompt 变更或回归通过。

七、验证与交付

设计准备模式：验证 Markdown 标题/代码块、文件与章节链接、任务依赖和检查追溯；报告修改文件、设计决策、覆盖缺口和后续依赖。明确没有新增实现、标注完成或真实评测结果，不输出虚构运行入口和数字。

最终执行模式：只运行相关最小验证，核对前置证据、划分/标注、四组配对、时间泄漏、指标手算、analysis_id/run_id 与安全记录关联、状态回归及 boundary/retention。报告真实命令、产物位置、hash、各检查证据和未完成项；只有 EVAL-C001–C004 全部有真实证据才可宣布阶段 E 完成。

两种模式均不修改原始业务数据、不连接真实业务系统、不提交/推送/发布 Git，不提前制作或伪造阶段 F 的展示数字。
